 System orchestration overview
Overview
The Smart Aquarium Monitoring System is built on a decoupled, stage-based batch pipeline architecture
optimized for 24/7 continuous operation on a Raspberry Pi 4B (2GB RAM).
Instead of monolithic scripts or competing background threads that fight for camera and CPU resources, the system
executes a structured 5-stage sequential monitoring cycle coordinated by master.py. Modules communicate
exclusively through atomic JSON files (storage/json_store.py) or return values passed by the orchestrator.
---

4. Atomic JSON Persistence (storage/json_store.py)
To prevent partial writes, file corruption during power cuts, or concurrent read/write collisions on the Raspberry Pi:
  Atomic Writes (save_json): Writes data to a temporary file via tempfile.mkstemp(), flushes and executes
 os.fsync(), then atomically renames/replaces it with os.replace().
 Thread & Process Safety: Wrapped in a reentrant lock (threading.RLock()).
  Automatic UTC Timestamping: Injects "timestamp": "2026-08-22T09:00:00Z" into dictionary payloads
 automatically.
 Backup Fallback (load_json): If a file is unreadable or corrupted, automatically falls back to .bak files.

B. 10-Sample Trimmed Mean Filter (pH & Turbidity)
To eliminate electrical noise from aquarium water pumps and LED drivers, analog pins A0 and A1 execute a
10-sample bubble sort, discard the 2 lowest and 2 highest readings, and return the average of the middle 6 samples:
 Code / configuration
float readAnalogSampled(int pin) {
  int buffer_arr[10];
  for (int i = 0; i < 10; i++) {
    buffer_arr[i] = analogRead(pin);
    delay(10);
  }
  // Bubble sort 10 samples
  for (int i = 0; i < 9; i++) {
    for (int j = i + 1; j < 10; j++) {
      if (buffer_arr[i] > buffer_arr[j]) {
        int temp = buffer_arr[i];
        buffer_arr[i] = buffer_arr[j];
        buffer_arr[j] = temp;
      }
    }
  }
  // Average the middle 6 samples
  unsigned long avgval = 0;
  for (int i = 2; i < 8; i++) {
    avgval += buffer_arr[i];
  }
  return (float)avgval / 6.0;
}
C. Calibrated Formulations
  pH Formulation:
 $$\text{Voltage} = \frac{\text{ADC} \times 5.0}{1023.0}$$
$$\text{pH} = 7.0 + \frac{2.50 - \text{Voltage}}{0.18}$$
  Turbidity Formulation:
 $$\text{NTU} = -1120.4 \times V^2 + 5742.3 \times V - 4352.9$$

Overview
The Computer Vision subsystem manages two dedicated camera streams:
 1. Camera 1 (Side View): Fish detection, centroid tracking, continuous 3-minute movement trajectory logging,
 behavioral dwell metrics, and centered ROI disease analysis.
2. Camera 2 (Top View): Surface feeding zone attendance monitoring, fish counting in the active RHS ROI, and hunger
 classification.
---
1. Camera Capture Modules
Side Camera (vision/side_camera.py)
  Single-Owner Pattern: The video device (/dev/video0 on Linux via V4L2 or default DirectShow on Windows) is
 opened and shared across tracking, behavior, and disease detection to prevent duplicate OpenCV handle locks.
 Synthetic Demonstration Fallback: If physical hardware is disconnected (or MOCK_CAMERAS=1), automatically
 generates a 30 FPS animated synthetic aquarium stream featuring simulated swimming fish, water level boundary
lines, and gravel level lines.
Top Camera (vision/top_camera.py)
  Strict Hardware Interface: Interfaces exclusively with Camera 2 (/dev/video2 or index 2).
  No Synthetic Fallback: Returns None when hardware is disconnected so feeding logic is never triggered erroneously
 by fake video feeds.

Key Technical Features:
 1. Pre-Inference Exclusion: To eliminate false positives from surface reflections and gravel pebbles, pixels in the top
 15% (WATER_LEVEL_PERCENT) and bottom 10% (GRAVEL_LEVEL_PERCENT) are zeroed out before inference.
2. Exponential Moving Average (EMA) Smoothing:
 $$\text{Box}_{\text{smooth}} = 0.70 \times \text{Box}_{\text{current}} + 0.30 \times \text{Box}_{\text{previous}}$$
Eliminates jitter and bounding box flicker across sequential frames.
 3. Persistent Identity Tracking: Tracks up to MAX_TRACKED_FISH = 4 individuals using Euclidean distance
 nearest-centroid matching with automatic track pruning for targets inactive $> 60\text{s}$.

4. Top-Camera Hunger Detection (vision/hunger_detector.py)
Monitors Camera 2 (Top View) during Stage 3 (3-minute observation):
A. Spatial Feeding Zone Partitioning
 Code / configuration
+-----------------------------------+-----------------------------------+
|     LEFT-HAND SIDE (LHS)          |       RIGHT-HAND SIDE (RHS)       |
|                                   |                                   |
|   Non-Feeding Zone (Ignored)      |     FEEDING AREA (Active ROI)     |

B. Temporal Averaging & Sustained Attendance Window
To avoid accidental food dispensing from transient pass-through fish:
  Requires Surface Attendance Ratio $\ge 30\%$ across the 3-minute window.
  Requires Average Feeding ROI Count $\ge 0.5\text{ fish}$.
  Evaluates discrete hunger tiers:
  $< 0.5\text{ avg fish} \implies \textbf{Normal / Not Hungry}$ ($0\text{ rotations}$).
  $0.5 \le \text{avg} < 1.5 \implies \textbf{Low Hunger}$ ($1\text{ rotation}$).
  $1.5 \le \text{avg} < 2.5 \implies \textbf{Moderate Hunger}$ ($2\text{ rotations}$).
  $\ge 2.5 \implies \textbf{High Hunger}$ ($3\text{ rotations}$).

05 — Automatic Feeder & MG90 Servo Controller
Overview
The automatic fish feeding subsystem controls an MG90 Micro Servo mounted on the aquarium food hopper, driven
by hardware pulse-width modulation (PWM) on GPIO Pin 12 (BCM).
Dispensing is triggered automatically at the end of Stage 3 (master.py::stage_hunger_and_feeding) based on
the sustained 3-minute surface attendance of fish in the feeding zone.

2. Multi-Backend Hardware PWM Drivers (feeding/servo.py)
To ensure robust operation across multiple Raspberry Pi OS versions (Debian 11 Bullseye, Debian 12 Bookworm,
Debian 13 Trixie), the driver features an isolated multi-backend execution engine:
 1. Backend 1 — RPi.GPIO / rpi-lgpio: Standard direct hardware PWM timer driver.
 2. Backend 2 — gpiozero.AngularServo: Pulse-width controlled abstraction ($0.5\text{ms} - 2.5\text{ms}$ pulse
 width).
3. Backend 3 — lgpio: Direct GPIO character device access.
 4. Backend 4 — Mock Fallback: Emulated software logging for development environments without physical GPIO.

4. Portion Calculations & Safety Limits
Portion Formula:
$$\text{Food Dispensed (g)} = \text{Rounds} \times \text{portion\_grams\_per\_turn}$$
Where portion_grams_per_turn = 0.05g (configurable in config.py and data/config.json).
Safety Safeguards:
 1. Daily Feed Limit (max_daily_feedings = 10): Prevents overfeeding if sensors glitch.
 2. Daily Food Weight Limit (max_daily_food_grams = 5.0g): Caps total dispensed food per day.
 3. Midnight Counter Reset: Daily totals reset automatically at 00:00:00 local time.
 4. Post-Feed Cooldown Timer (post_feed_cooldown_minutes = 30):
  After dispensing, the feeder enters a mandatory 30-minute cooldown.
  During cooldown, Stage 3 bypasses top-camera feeding checks to allow fish to consume dispensed food.
  The cooldown timestamp is stored atomically in data/latest_feed.json and survives system restarts or power
 cycles.
 Handles NTP clock drift / clock skew automatically.

CHAPTER 06
06 — Firebase Cloud Synchronization & Android
App Bridge
Overview
The cloud synchronization subsystem connects the edge Raspberry Pi to Firebase Realtime Database (RTDB) using
the official Firebase Admin Python SDK.
It performs bidirectional communication:
  Upstream: Uploads real-time state telemetry, sensor readings, behavioral metrics, disease diagnoses, and feeding
 histories.
 Downstream: Retrieves natural language symptom descriptions submitted by users from the companion Android
 mobile app.
---
1. Firebase Initialization & Credentials (utils/firebase.py)
The bridge checks for service account credentials in the following search order:
 1. serviceAccountKey.json (Project Root)
 2. firebase_credentials.json (Project Root)
 3. data/serviceAccountKey.json
 4. data/firebase_credentials.json
 
Initialization Call:
 Code / configuration
import firebase_admin
from firebase_admin import credentials
cred = credentials.Certificate(str(FIREBASE_CREDENTIALS_PATH))
firebase_admin.initialize_app(cred, {"databaseURL": FIREBASE_DATABASE_URL})
If credentials are absent or the network is offline, all cloud calls fail gracefully without interrupting local edge monitoring
or servo actuation.
